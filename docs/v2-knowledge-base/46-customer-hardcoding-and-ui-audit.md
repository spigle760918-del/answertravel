# AnswerTravel V2 客户硬编码与界面信息架构审计

状态：审计完成，代码未修正

日期：2026-09-17

审计范围：`v2/src`、`v2/scripts`、`v2/web`、相关知识库和 Git 历史

审计目的：在修正代码前识别客户绑定、Provider 绑定、界面栏目来源和外部项目影响。

## 1. 总结

- 数据层具备真实多租户骨架：核心表包含 `tenant_id`，主要业务表启用 PostgreSQL RLS，仓储普遍使用租户事务；
- 应用层并未完全平台化：若干通用模块直接包含北京珈程名称、官网、证件、备案号、问题快照和页面路径；
- 北京珈程专属生产脚本和 fixture 本身可以保留，但其位置与依赖边界不清；
- 当前 Web 页面没有证据表明复制了某一个外部网站；它由提交 `6cd3eda` 首次建立，并按后续功能切片逐个增加栏目；
- 当前页面本质上是“工程和业务验收台”，不是经过独立产品信息架构设计的多客户 SaaS 主界面；
- 修复前应先抽取客户 profile 和第二租户契约，然后分离客户产品界面与内部验收界面。

### P2：Provider 与阶段性部署绑定

- 观察模块默认 `deepseek-chat`，符合当前单 Provider Alpha，但不是长期平台能力；
- Web 中多处固定显示“DeepSeek API”和“单品牌 Alpha”；
- Provider 固定在证据链中可以保留，但计划创建、状态标签和页面栏目应读取实际 Provider/终端；
- 当前问题生成服务也固定 DeepSeek，后续应通过 Provider 适配器配置，而不是为每个模型复制模块。

### 可接受的客户引用

以下位置允许出现北京珈程，但必须列入允许清单：

- 客户 profile、生产 seed、历史恢复脚本；
- 契约/集成测试中的真实客户回归样例；
- 知识库中的历史事实与验收记录；
- 不会被通用运行时导入的快照和 fixture。

## 3. 界面、栏目和频道来源审计

### 3.1 是否对标或复制某个网站

当前仓库没有证据表明 Web 界面直接复制 GEOFlow、`yao-geo-skills`、`geo-citation-lab` 或其他具体网站：

- `v2/web/src/App.tsx` 与 `styles.css` 在提交 `6cd3eda` 中首次创建；
- 该提交同时创建《V2 可视化验收台》意图卡和浏览器验收截图；
- Web 依赖只有 React/Vite 等基础工具，没有引入外部项目 UI 组件包或主题包；
- 样式为本仓库本地 CSS，未发现外部品牌素材、远程样式、复制声明或来源注释；
- 知识库把 GEOFlow、`yao-geo-skills` 和 `geo-citation-lab` 定义为业务方法、契约或研究参考，没有将其列为 UI 原型。

因此现有证据支持的结论是：**界面采用常见后台仪表盘形态，但无法归因于某一个被对标网站。**

### 3.2 当前栏目是如何形成的

最初验收台只有四个栏目：

1. 项目概览；
2. 品牌真相；
3. 游客问题；
4. 采集与回答。

后续栏目随代码切片逐次加入：真实品牌接入、GEO 情报、决策建议、品牌描述核验、优化行动、可比较周期。当前共十个固定 Tab。

这说明栏目不是从一个完整客户旅程或竞品网站信息架构反推出来的，而是按照开发完成顺序累积。它适合查看“我们开发了什么”，不一定适合客户完成“我今天该做什么”。

### 3.3 当前固定界面细节

| 固定细节 | 问题 |
| --- | --- |
| `tabs` 在 `App.tsx` 中固定为十个 | 无权限、角色、租户成熟度或功能开关驱动；每完成一个模块就增加频道 |
| “当前品牌空间”仅显示名称 | 看起来像品牌切换器，但当前没有切换能力 |
| 整页只请求 `/api/acceptance/overview` | 所有栏目依赖单一超大验收接口，不是产品 API 边界 |
| 项目概览展示 Linux CI、阿里云、备份、告警等 | 混合客户业务价值与内部工程上线证据 |
| 页面固定显示 Alpha、DeepSeek API | 属于当前部署/Provider 状态，不应成为长期产品栏目定义 |
| 大量状态与行业文案写在单个 `App.tsx` | 难以按角色、客户和功能版本治理 |
| 无登录、组织、用户、角色、租户选择路由 | 当前是单租户只读验收入口，不是完整客户工作台 |
| 导航使用本地 state 而非真实路由 | 无可分享栏目 URL、权限路由和页面级加载边界 |

### 3.4 可以保留的界面原则

- 证据可下钻、失败不隐藏；
- 事实、推断和建议分级；
- 品牌真相、问题、观察、诊断和行动形成闭环；
- 非技术业务语言优先；
- 不用模拟数字填充空状态。

这些原则来自 AnswerTravel 产品章程，和某个具体外部网站无关。

## 4. 修正代码前的推荐决策

### 阶段 0：冻结扩张

- 暂停新增珈程专属官网实施能力；
- 不删除、不改写现有生产数据和历史证据；
- 不把当前验收台直接包装成多客户正式产品。

### 阶段 1：建立客户 profile 契约

先定义但不迁移生产数据：

- 品牌身份和别名；
- 官网及页面目标；
- 可核验证件/事实断言；
- 信源目标与允许域名；
- 问题快照和观察策略；
- Provider、预算与授权。

### 阶段 2：清理 P0 通用模块

按风险顺序处理：

1. 验收台品牌名称判断；
2. 官网诊断目标和识别规则；
3. 修复蓝图与信源蓝图中的客户事实；
4. 信源核验目标；
5. 内链识别和品牌主张核验规则。

### 阶段 3：迁移客户专属资产

- 将珈程事实包、问题快照、生产计划移入明确的客户 profile/seed 区域；
- 保留原稳定 ID、授权标记和历史脚本兼容入口；
- 平台代码只读取通用契约。

### 阶段 4：第二租户证明

建立一个不含珈程名称、域名和证件的隔离测试租户，验证：

- 不改源码即可完成品牌接入；
- 官网诊断不会访问 `jiacheng666.com`；
- 蓝图不会出现珈程事实；
- 验收台能正确展示第二品牌；
- 两租户数据与队列严格隔离。

### 阶段 5：重新设计产品信息架构

在不丢失验收证据的前提下拆成两类界面：

- 客户工作台：概览、品牌资产、AI 可见度、问题与受众、机会与行动、内容/网站/信源、监测与复测；
- 管理员验收台：采集运行、原始证据、失败、费用、部署、备份、CI 和告警。

栏目最终名称和顺序应在第二租户测试后单独做 Gate A，不在平台化重构中顺手决定。

## 5. 当前决定

- 立即采用 ADR 中的平台—客户边界；
- 本审计作为代码修正前基线；
- 下一步先设计客户 profile 契约与第二租户验收场景；
- 在用户确认修复计划前，不修改运行代码，不部署，不触碰北京珈程官网。
