# AnswerTravel V2 严格 Vibe Coding SOP

状态：已确认  
版本：1.0  
日期：2026-09-13

## 1. 对 Vibe Coding 的定义

本项目中的 Vibe Coding 是“业务意图用自然语言驱动，工程约束由系统化门禁保障”。它不等于凭感觉连续生成代码。

原则：

- 先把意图固化为可验收契约，再生成代码；
- 每次只完成一个可演示、可测试、可回滚的垂直切片；
- AI 承担架构翻译、实现、测试、文档和风险检查；
- 用户主要确认业务结果和关键边界，不承担细碎技术决策；
- 代码、测试、证据和知识库必须同步更新。

## 2. 总体启动门禁

V2 编码开始前必须依次完成：

1. 产品章程确认；
2. 总体架构确认；
3. 本 SOP 确认；
4. 核心指标契约确认；
5. 第一阶段范围和“不做什么”确认；
6. 技术 Spike 验证关键不确定性；
7. 建立 CI、测试、迁移、审计和发布骨架。

用户只需要确认业务层结果。技术选择由 AI 提供推荐默认值、理由和风险；只有会改变成本、能力或合规边界时才请求用户决定。

## 3. 每个模块的标准循环

### Gate A：意图卡

AI 先给出一页以内的模块意图卡：用户问题、输入、输出、边界、失败方式、自动化等级和验收标准。用户只回答 Yes/No 或指出业务偏差。

### Gate B：契约与样例

先定义 API/事件/数据契约和 3 类样例：正常、边界、失败。AI 标出事实和推断来源。

### Gate C：最小真实垂直切片

从界面到 API、数据库、任务和审计完成一条真实路径。演示数据只能存在于明确隔离的 fixture/test 环境。

### Gate D：自动评测

至少通过：

- 单元测试；
- 模块契约测试；
- 数据迁移与回滚测试；
- 关键端到端测试；
- AI 输出评测与事实性检查；
- 权限、安全、失败重试和幂等测试；
- 性能、费用和可观察性检查（按风险选择）。

### Gate E：业务验收

向用户展示真实业务结果、下钻证据和失败状态，而非代码细节。用户 Yes/No。

### Gate F：封版与记忆

更新决策日志、指标口径、已知限制、测试证据和下一切片。没有完成知识库更新，不算完成模块。

## 4. 变更分级

| 级别 | 示例 | 是否需要用户再次确认 |
| --- | --- | --- |
| C0 内部实现 | 重构、性能、测试补充，不改变行为 | 否 |
| C1 模块行为 | 新字段、新筛选、新告警，保持章程 | 模块验收时 Yes/No |
| C2 产品边界 | 新用户角色、新自治等级、新外部发布渠道 | 是 |
| C3 推翻性变更 | 改核心数据链、指标定义、架构形态 | 必须先更新架构/ADR，再确认 |

## 5. AI 生成代码的硬门禁

- 不允许从一句模糊需求直接修改多个模块；
- 不允许生产路径调用未版本化 Prompt；
- 不允许指标定义只存在于前端代码；
- 不允许前端生成业务事实或趋势；
- 不允许覆盖不可变原始证据；
- 不允许隐藏失败样本或只展示成功结果；
- 不允许以定时延迟模拟发布、收录或效果；
- 不允许绕过迁移、审计、测试和回滚；
- 不允许将第三方示例数据当成自身真实能力证据。

## 6. 推荐实施顺序

1. 工程与证据骨架；
2. 品牌真相中心；
3. AI 问题智能与问题组版本；
4. 单 Provider 重复采样和不可变回答；
5. 引用/页面证据；
6. 品牌与竞品同口径指标；
7. 决策引擎与竞对深挖；
8. 内容/页面行动工作室；
9. 第一个真实发布适配器；
10. 发布前后实验与复测；
11. 第二、第三 Provider；
12. 自治执行、热点雷达和规模化运营。

先证明一条真实闭环，再横向扩展模型和渠道。

## 7. Definition of Done

一个切片只有同时满足以下条件才算完成：

- 验收场景通过；
- 真实数据与 fixture 明确隔离；
- 所有输出可追溯；
- 自动化测试通过；
- 失败、重试和回滚可验证；
- 费用和运行状态可观察；
- 安全与权限检查完成；
- 用户可用行业语言理解结果；
- 知识库和决策日志已更新；
- 未知问题和证据不足被明确显示。
