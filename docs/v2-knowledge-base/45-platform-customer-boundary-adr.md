# ADR：AnswerTravel 平台、租户与客户资产边界

状态：已确认，代码修正尚未开始  
日期：2026-09-17  
决策类型：架构边界修正  
触发原因：北京珈程作为首个真实客户实例进入生产闭环后，部分客户事实进入了通用模块，偏离多租户平台基线。

## 1. 决策

AnswerTravel V2 是面向多个文旅客户的 GEO 平台。北京珈程是首个真实生产租户、验收案例和客户数据包，不是产品本身，也不是通用业务规则的默认模型。

固定关系如下：

```text
AnswerTravel 平台（geo.21y.com）
  ├─ 租户/品牌空间 A：北京珈程
  │    ├─ 品牌事实、问题组、官网、信源、观察计划与结果
  │    └─ 客户专属初始化、授权记录和生产恢复脚本
  ├─ 租户/品牌空间 B：未来旅行社、景区、酒店或目的地客户
  └─ 平台能力：租户隔离、证据、采样、诊断、决策、行动、发布与复测
```

## 2. 四层边界

### 2.1 平台内核

适用目录包括通用领域模块、平台服务、API、Worker、数据库迁移和通用 Web 组件。

平台内核必须：

- 只通过租户上下文、版本化契约和仓储读取客户资料；
- 对品牌名称、别名、官网、证件、备案、问题组、Provider 和页面目标使用输入或配置；
- 保持 RLS、不可变证据、审计、费用和权限门禁；
- 能在不修改源码的情况下运行第二个客户。

平台内核禁止出现：

- 客户名称、域名、许可证、统一社会信用代码、备案号和产品名称字面量；
- 以品牌名称判断环境、真实性、权限或流程状态；
- 固定客户 URL、页面路径、信源目标和客户问题快照；
- 由客户专属模块反向决定通用 Schema 或通用状态枚举。

### 2.2 租户配置与客户资料

客户资料必须是版本化、可追溯的租户数据，至少包括：

- 品牌身份、别名、官网和允许访问的域名；
- 事实、证件、产品、禁用表达和公开范围；
- 监测问题组、Provider 策略、预算和区域语言；
- 官网诊断目标、信源核验目标和页面类型映射；
- 客户授权、实施权限和发布权限。

这些内容优先进入数据库；部署时必须存在的最小内容可以进入明确命名的客户配置包，但不得进入通用模块。

### 2.3 客户实例资产

以下内容允许专属于北京珈程，但必须和平台内核物理隔离：

- 已批准问题快照；
- 生产初始化和一次性恢复脚本；
- 真实事实包与历史授权标记；
- 客户专属验收 fixture、部署 profile 和回归样例。

客户资产可以依赖平台契约；平台内核不得反向导入客户资产。

### 2.4 产品界面与内部验收界面

- 客户产品界面以客户任务和业务结果组织栏目，不以内部开发切片、CI、迁移或服务器门禁作为主导航；
- 内部验收、部署状态和工程证据必须进入独立的管理员/验收区域；
- “当前品牌空间”必须来自真实租户上下文。未实现切换能力时不得伪装成可切换控件；
- Provider 名称只在证据、费用或终端边界需要时展示，不应成为通用栏目定义。

## 3. 依赖方向

唯一允许的依赖方向：

```text
客户 profile / seed / fixture
            ↓
通用应用服务与领域契约
            ↓
平台内核、数据库、队列和证据设施
```

禁止通用领域模块导入 `jiacheng-*` 或任何其他客户命名文件。

## 4. Alpha 单品牌的正确解释

“单品牌 Alpha”只限制本次部署和商业验证规模，不改变多租户平台架构：

- 可以只创建一个生产租户；
- 可以暂不提供客户自助切换和完整商业化权限后台；
- 不可以在通用代码中写死该租户；
- 不可以用首个客户的官网结构、证件或问题组定义所有客户的产品模型。

## 5. 新硬门禁

后续任何业务代码修正必须同时满足：

1. 通用目录客户字面量扫描为零，允许清单只覆盖客户 profile、fixture、测试和迁移说明；
2. 至少两个不同品牌 fixture 运行同一服务契约；
3. 第二租户无需修改源码即可完成品牌接入、问题组、观察和官网诊断最小流程；
4. 客户 A 的域名、证件、问题和信源不得出现在客户 B 输出中；
5. 产品 UI 与内部验收 UI 的信息架构和权限边界明确；
6. 新客户接入只新增数据或客户 profile，不新增复制粘贴的客户专属领域模块；
7. 修正不得改写既有不可变生产证据，历史珈程记录继续保留。

## 6. 迁移原则

- 先审计、再设计配置契约、再迁移代码；
- 优先做无行为变化的抽取，不在同一步重做产品 UI；
- 珈程现有生产 ID、证据哈希、计划、回答和诊断保持不变；
- 客户专属脚本先移动和降级为 profile/seed，再替换通用模块中的字面量；
- 每一阶段均需第二租户回归测试和生产只读验证；
- 在平台化门禁通过前，暂停新增珈程专属官网实施功能。

## 7. 后果

正面结果：

- 恢复 AnswerTravel 作为多客户平台的产品边界；
- 保留北京珈程真实闭环和生产证据；
- 新客户接入从“改源码”变为“建租户、导入资料、授权运行”；
- 客户产品界面不再等同于工程验收台。

代价：

- 需要抽取客户 profile、官网目标和信源核验契约；
- 需要拆分产品 UI 与管理员验收信息；
- 部分已封版切片需要做兼容性重构，但不得篡改历史业务验收记录。
