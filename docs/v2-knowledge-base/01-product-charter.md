# AnswerTravel V2 产品章程

状态：已确认  
版本：1.0  
日期：2026-09-13

## 1. 产品使命

建设面向文旅目的地、旅行社、景区、酒店及文旅服务品牌的 AI 原生 GEO 系统。系统不是一个只展示提及率的看板，而是一个能够自主发现机会、判断根因、生成行动、执行低风险动作并持续验证的 GEO 运营系统。

核心闭环：

`品牌真相 → 游客问题发现 → 多模型重复采样 → 回答与引用证据 → 品牌/竞品/网站诊断 → AI 决策 → 内容/页面/信源/业务动作 → 审批与发布 → 固定问题集复测 → 学习迭代`

## 2. 目标用户

目标用户是文旅行业从业者，不要求具备开发、数据或 Prompt 工程经验。界面和流程必须使用行业语言，而不是工程术语。

主要用户：

- 文旅品牌负责人；
- 市场、品牌和内容负责人；
- 目的地运营和旅行社产品负责人；
- 少量负责合规、技术和发布接入的管理员。

## 3. 人与 AI 的职责

### 人必须提供或确认

- 企业、品牌、产品、服务和目的地的真实基础信息；
- 品牌名称、别名、实体关系和官方资产；
- “人无我有、人有我优”的产品与服务颗粒度；
- 可公开事实、敏感事实、禁用表达和合规边界；
- 热点发生后，品牌确实做过或能够做出的正向能力动作；
- 预算、渠道、业务优先级和最终发布权限；
- 高风险动作的 Yes/No 决策。

### AI 默认完成

- 根据游客旅前决策链拓展问题、聚类、去重和分层；
- 维护固定问题组、轮换问题组、热点问题组和竞对深挖问题组；
- 多模型、多终端重复采样、失败重试和成本调度；
- 品牌/竞品提及、条件化排名、主张级情感和风险分析；
- 引用选择、引用吸收、域名、文章、作者和页面结构分析；
- 官网可抓取性、实体一致性、证据密度、页面结构和新鲜度诊断；
- 判断差距更可能属于事实、产品、内容、结构、信源、口碑或采样问题；
- 生成行动候选、内容任务书、页面蓝图和复测计划；
- 在政策允许范围内自动执行可逆、低风险动作；
- 发布后按原问题组复测，报告变化及不确定性。

## 4. AI 自治等级

| 等级 | 行为 | 默认规则 |
| --- | --- | --- |
| A0 观察 | 采集、保存、计算、告警 | 自动 |
| A1 建议 | 给出方向、根因、优先级和预计影响 | 自动生成 |
| A2 草拟 | 生成问题组、任务书、文章、页面方案、发布计划 | AI 完成，人 Yes/No |
| A3 受控执行 | 执行可回滚、低风险、已授权动作 | 策略内自动，完整审计 |
| A4 高风险执行 | 正式发布、删除、对外联络、敏感或危机内容 | 必须人工确认 |

系统目标不是让人逐字段编辑，而是让人维护真相、处理例外和做少量关键确认。

## 5. 问题智能

品牌下的游客问题必须由 AI 参与拓展。输入至少包括：

- 品牌、目的地、产品和竞品；
- 旅前阶段：灵感、比较、计划、预订、风险确认；
- 人群：亲子、老人、情侣、学生、入境游客等；
- 场景：季节、节假日、预算、天数、交通、住宿、玩法；
- 决策疑虑：是否靠谱、是否适合、优缺点、避坑、投诉和保障；
- 热点和品牌真实响应能力。

推荐默认问题组合：

- 60% 固定基准问题：保证长期趋势可比较；
- 25% 轮换探索问题：发现新需求与内容机会；
- 15% 热点/事件/竞对触发问题：快速验证变化。

中性品类问题、品牌问题和竞品问题必须分组，防止诱导式问题污染品牌提及率。

## 6. AI 决策必须输出什么

每次决策至少包含：

- 观察到的事实和样本范围；
- 与竞品的同口径差距；
- 置信度和可能的替代解释；
- 根因分类；
- 可选动作及“不行动”选项；
- 建议动作、成本、风险、负责人和预计窗口；
- 是否需要竞对深度追踪；
- 需要人补充的最少信息；
- Yes/No 审批项；
- 发布前基线和发布后复测设计。

## 7. 高标准底线

- 不以一次回答代表模型长期表现；重要问题必须重复采样。
- 竞品比较必须保持问题、模型、终端、区域、时间窗和轮次同口径。
- 只有列表或明确推荐顺序存在时才计算排名，否则返回 `不适用`。
- 情感必须细化到主张或品牌描述，不能仅凭整篇回答做粗暴正负面。
- 区分“被列为来源”“内容被答案吸收”“正文里出现链接”。
- 所有结论显示样本量、失败率、时间、模型/终端版本和不确定性。
- 发布后变化只报告关联和证据强度，不在缺少实验设计时宣称因果。
- 不生成虚假体验、评论、数据、资质、承诺或引用。

## 8. 非目标

- 不做刷榜、诱导模型、垃圾外链或批量伪内容系统；
- 不把搜索引擎收录等同于 AI 可见度提升；
- 不用漂亮模拟数据代替真实采集；
- 不要求文旅用户管理复杂模型参数、队列或数据库；
- V2 首阶段不采用大规模微服务拆分。
