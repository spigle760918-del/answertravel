# 意图卡：产品壳层与只读证据闭环 V1

状态：Gate A-F 已完成并封版

日期：2026-09-20

依据：`45-platform-customer-boundary-adr.md`、`48-geoflow-agpl-frontend-integration-adr.md`、`49-product-scope-convergence-adr.md`、`50-final-product-ui-and-implementation-adr.md`

## 1. 为什么现在做

最终信息架构和主要页面已经完成逐页确认，但当前运行页面仍是单个 `App.tsx` 驱动的工程验收台，所有内容只读取 `/api/acceptance/overview`，没有真实页面路由、产品级 API、明确的租户上下文或客户工作台与管理员验收台边界。

首批施工必须先建立稳定产品壳层和最短的真实证据链：

```text
总览
→ 游客问题组
→ 监测计划/运行记录
→ 原始回答详情
```

这样可以先证明用户看到的每个汇总都能下钻到真实问题、计划、尝试和回答，再继续建设分析、竞品、决策和复测页面。

## 2. 本切片用户结果

文旅品牌负责人进入当前品牌空间后，可以：

1. 在总览看到当前监测范围、最近运行、有效/失败样本和下一步；
2. 查看已批准游客问题组及版本、问题类型和纳入状态；
3. 查看监测计划、采集口径、轮次、预算、成功/失败和 Token；
4. 从计划进入运行记录，再进入单条原始回答；
5. 核对回答全文、问题、轮次、模型、采集方式、时间、Token、尝试和证据标识；
6. 在没有数据、部分失败、无权限或服务错误时看到真实状态，不出现模拟指标。

本切片全部为只读，不创建问题组、不执行监测、不重试、不补采、不审批、不发布。

## 3. 首批页面与路由

| 路由 | 页面 | 主要内容 |
| --- | --- | --- |
| `/overview` | 总览 | 当前品牌、批准问题组、最近计划、成功/失败样本、Token、证据新鲜度和明确下一步 |
| `/monitoring/questions` | 游客问题管理 | 问题组版本、状态、问题文本、问题类型、分组角色、纳入/排除及原因 |
| `/monitoring/plans` | 监测计划 | 计划列表、问题组版本、平台、模型、采集方式、轮次、样本、预算、授权和时间 |
| `/monitoring/runs/:planId` | 运行记录详情 | 目标及尝试状态、失败代码、Token、轮次、时间和回答入口 |
| `/evidence/answers/:answerId` | 原始回答详情 | 问题、回答全文、采集上下文、Provider 结果摘要、哈希、尝试和已有分析/引用状态 |
| `/admin/acceptance` | 原验收台兼容入口 | 保留当前工程与生产验收信息，不作为客户首页 |

导航只显示本切片真实可用页面。后续冻结栏目不创建空白菜单、假按钮或“敬请期待”页面。

## 4. 只读 API 契约

新增版本化页面 API；旧 `/api/acceptance/overview` 在本切片保留，仅供 `/admin/acceptance` 回滚使用。

建议首批接口：

| 方法与路径 | 作用 | 主要事实源 |
| --- | --- | --- |
| `GET /api/v1/workspace` | 当前租户、品牌名、用户可见权限和数据环境 | 服务端租户上下文、租户/品牌配置 |
| `GET /api/v1/overview` | 首屏只读摘要 | 问题组、观察计划、目标、尝试、回答 |
| `GET /api/v1/question-panels` | 问题组版本列表 | `question_panels` |
| `GET /api/v1/question-panels/:panelId/versions/:version` | 问题组详情 | `question_panels` |
| `GET /api/v1/observation-plans` | 监测计划分页列表 | `observation_plans` 与聚合计数 |
| `GET /api/v1/observation-plans/:planId` | 计划与运行详情 | 计划、目标、尝试、回答 |
| `GET /api/v1/raw-answers/:answerId` | 原始回答详情 | `raw_answers`、目标、尝试和只读证据状态 |

契约要求：

- 浏览器不得提交或覆盖 `tenantId`；租户必须由可信服务端上下文解析；
- 所有仓储读取继续在 PostgreSQL RLS 租户事务中执行；
- 列表接口必须分页、稳定排序，并限制最大页大小；
- API 使用稳定代码表达空、错、无权限和不存在，不向浏览器返回堆栈、数据库结构、密钥或原始认证头；
- 总览只返回该页需要的摘要，不再复制验收接口的全部业务对象；
- 回答详情不得暴露 Provider 密钥或敏感请求头；原始 Provider 载荷只返回经过契约允许的字段；
- 所有时间使用带时区的 ISO 8601，Token 与失败计数来源于真实尝试；
- API 类型与前端类型从同一版本化契约生成或共同验证，禁止复制后逐渐漂移。

## 5. 租户、身份与权限边界

当前生产入口只有服务端配置的验收租户，没有完整登录、组织成员和租户切换能力。本切片不得把这一现状包装成已经完成的多租户账号系统。

固定规则：

1. 本地和隔离验收可以使用服务端固定的只读测试租户；页面明确显示当前品牌空间，但不显示虚假切换器；
2. API 不接受查询参数、路径参数、Header 或浏览器存储中的任意租户 ID；
3. 使用两个不同品牌 fixture 验证相同页面和 API 契约，分别启动或注入服务端租户上下文；
4. 新客户工作台不得在无身份保护的情况下替换公网首页；
5. 生产开放前必须另立身份与会话决策，完成登录、成员关系、角色、服务端租户解析、CSRF/CORS、会话失效与审计验收；
6. 在上述生产身份门禁通过前，本切片最多完成本地/隔离预览和构建产物，不部署为公开客户入口。

## 6. 前端与 GEOFlow AGPL 交付边界

前端必须基于固定 GEOFlow 版本 `abcc638887dd35f508a59815f01ed42bc4415a09` 的实际源码和设计变量施工，不再从静态预览反向手写一套近似样式。

施工前必须固定：

- 独立的 AGPL 前端源码根目录与构建边界；
- `AGPL-3.0-only` 许可证文本、上游版权和固定提交记录；
- 上游来源记录文件（实施时创建），记录上游地址、提交、保留文件和修改清单；
- 页面可访问的“对应源码”入口及其版本/提交；
- 前端构建产物到源码提交的可追溯清单；
- AnswerTravel 后端保持独立构建和接口边界，不把 GEOFlow 的 PHP/Laravel 数据模型作为业务事实源。

本切片复用范围仅为：公共侧栏、顶栏、页面头部、表格、筛选、状态、详情、空状态、抽屉和响应式交互。不得因上游存在内容、分发、站群或网站设置页面而带入 AnswerTravel。

## 7. 页面状态与业务语言

五个客户页面均必须覆盖：

- 加载中；
- 首次无数据；
- 筛选无结果；
- 部分成功；
- 服务错误；
- 不存在；
- 无权限；
- 当前能力未接入。

具体要求：

- 空状态说明缺少哪一步，并只给出当前真实可用的下一步；
- 失败记录和成功记录同等可见，不用“完成”掩盖部分失败；
- 当前只有 DeepSeek API 时如实显示，不出现其他平台徽标或模拟数据；
- 不显示尚未具备可比性的趋势、平台对比、竞品百分比或综合评分；
- 工程术语只出现在管理员验收入口，客户页使用问题、计划、运行、回答和失败原因等业务语言；
- 当前品牌、页面标题、筛选和主操作沿用已确认的 GEOFlow 密集运营布局。

## 8. 多租户与客户硬编码修正范围

本切片只修复支撑上述五个只读页面所必需的客户绑定，不顺手迁移全部历史客户专属模块。

必须完成：

- 新页面和新 API 中不得出现北京珈程名称、域名、证件、固定 ID 或固定问题字面量；
- 品牌名称来自当前租户的真实品牌数据；
- 通用前端不得导入 `jiacheng-*` 客户文件；
- 至少两个品牌 fixture 通过同一套页面/API 测试；
- 客户 A 的名称、问题、计划和回答不能出现在客户 B 响应或页面缓存中；
- 租户上下文变化时先清除旧数据，再加载新数据，不闪现上一租户内容。

不在本切片处理官网诊断、信源核验、结构修复蓝图等模块的全部 P0/P1 硬编码；这些仍按 `46-customer-hardcoding-and-ui-audit.md` 分阶段修正。

## 9. 实施顺序

Gate A 通过后按以下顺序施工，不并行扩大范围：

1. 锁定 GEOFlow 上游源码、许可证、修改记录和独立构建目录；
2. 定义 `workspace`、总览、问题组、计划/运行和回答详情的版本化响应契约；
3. 建立服务端租户上下文和页面级只读仓储，不改变既有表和历史证据；
4. 完成 GEOFlow 公共壳层、真实路由和只读导航；
5. 完成总览 → 问题组 → 计划/运行 → 原始回答的下钻；
6. 实现所有空、错、无权限和部分成功状态；
7. 建立双租户 API、缓存隔离和浏览器测试；
8. 生产构建与安全检查通过后，只打开本地或隔离预览供 Gate E 验收；
9. Gate E 通过后仍不自动部署公网，生产身份与切换必须单独授权。

## 10. 自动化测试与人工验收

### 契约与服务测试

- 每个新 API 的成功、空数据、404、无权限和依赖失败；
- 客户不能通过输入更改租户；
- RLS 下跨租户资源返回不可见，而不是泄漏存在性；
- 汇总数与原始计划、目标、尝试和回答一致；
- 失败与 Token 聚合不会重复计数；
- 原始回答保持不可变，不因读取或页面操作产生写入；
- 响应不含密钥、数据库地址、认证头、内部堆栈和受限品牌事实。

### 浏览器验收

- 桌面和常用手机宽度无重叠、截断或横向溢出；
- 侧栏、顶栏、面包屑、列表、筛选、分页、详情和返回路径可用；
- 从总览能够进入问题组、计划/运行及一条真实回答；
- 刷新和深链接仍在正确页面；
- 加载、空数据、部分失败、错误、404 和无权限均可复现；
- 键盘操作、焦点、关闭按钮和基本无障碍检查通过；
- 页面不出现模拟数字、未接入平台或北京珈程通用硬编码；
- AGPL 许可证、上游信息和对应源码入口可访问。

### Gate E 展示

向用户实际打开至少以下视图：总览、游客问题、监测计划、运行记录、原始回答、空数据、部分失败和手机布局。不能只用测试日志或截图摘要替代交互验收。

## 11. 可观察性与失败恢复

- 新 API 记录路由、结果状态、耗时、当前租户内部标识和事件 ID，但不记录回答全文、密钥或敏感事实；
- 页面错误向用户显示可报告的事件编号；
- 新前端静态资源使用可追溯版本并支持整体回退；
- API 变更为新增版本化路由，不删除旧验收接口；
- 数据库原则上不需要新迁移；若实施中确需迁移，必须停止并单独说明原因和回滚，再进入迁移门禁；
- 任何读取路径不得触发队列、模型调用、抓取、诊断重算或数据库写入。

## 12. 回滚方案

- 保留旧 Web 构建产物和 `/admin/acceptance` 兼容入口；
- 新前端按独立版本构建，发生问题时整体切回上一版本，不回滚数据库；
- 新 `/api/v1/*` 为附加路由，回滚时可停止暴露，不影响 `/health/*` 和旧验收 API；
- 不修改历史回答、计划、失败、引用、诊断和授权记录；
- 未通过生产身份门禁前不替换公网客户首页，因此本切片 Gate E 失败不会影响当前生产服务。

- 不实现周期监测写操作、其他 AI 平台或网页/App 采样；
- 不实现竞品分析、竞争范围、信源分析、诊断、决策、行动或复测页面；
- 不实现 AI 工作台执行能力；
- 不实现完整登录、组织管理或租户切换器，也不带着该缺口公开上线；
- 不建立 CMS、内容工厂、素材库、分发、流量归因或 CRM；
